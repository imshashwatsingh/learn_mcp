# Project: Custom Skill + Context MCP Server

## Goal

Build two small, practical AI-native developer tools:

1. A custom OpenCode skill/slash command that automates a repetitive coding task.
2. A small MCP server called **Context Summarizer** that exposes useful context-management tools to an AI coding assistant.

The implementation should be intentionally small, clean, understandable, and runnable.

Do not over-engineer the solution.

# Part 1 — Custom OpenCode Skill / Slash Command

## Task selection

Choose one genuinely useful repetitive software-engineering task.

Prefer:

> **Generate a PR description from the current Git diff**

This is the recommended task because it demonstrates useful judgment rather than simply generating boilerplate.

The command should:

1. Inspect the current Git state.
2. Inspect the relevant diff.
3. Understand the changed files and intent.
4. Generate a concise PR description.
5. Include:

   * Summary
   * What changed
   * Why it changed
   * Testing performed
   * Important implementation details or risks
6. Avoid inventing changes or tests.
7. Clearly state when information cannot be determined from the repository.
8. Produce output suitable for copying into a GitHub/GitLab pull request.

Use OpenCode's native custom command/skill mechanisms rather than inventing a custom framework.

OpenCode supports project-local commands in:

`.opencode/commands/`

and skills in:

`.opencode/skills/<skill-name>/SKILL.md`.

Use the current OpenCode documentation and repository conventions when deciding between a command and a skill.

Reference:

https://opencode.ai/

Relevant official documentation:

* Skills: https://opencode.ai/v2/docs/skills
* Commands: https://dev.opencode.ai/docs/commands/
* MCP servers: https://opencode.ai/v2/docs/mcp-servers

## Deliverables

Create the custom command/skill in the repository.

Prefer a simple command such as:

`.opencode/commands/pr-description.md`

or, if a skill is more appropriate:

`.opencode/skills/pr-description/SKILL.md`

The implementation must be directly usable from OpenCode.

If using a command, make it callable as something similar to:

`/pr-description`

If using a skill, make sure it is discoverable and usable through OpenCode's skill mechanism.

The prompt must dynamically inspect the repository rather than relying on hard-coded project details.

Use `$ARGUMENTS` only if it provides genuine value.

# Required MCP Tools

Implement at least these three tools.

## 1. summarize_context

Tool name:

`summarize_context`

Purpose:

Take a chunk of text and return a concise summary.

Input should include something similar to:

```text
text: string
```

Optional parameters may include:

* max_length
* style
* focus

but do not add unnecessary complexity.

The result should contain a concise, useful summary.

The implementation should be structured so that the summarization logic can call an LLM.

Use an environment variable for the model/API configuration rather than hard-coding secrets.

For example, support an environment variable such as:

`OPENAI_API_KEY`

If an LLM API is not configured, provide a clear error message or a deterministic fallback where appropriate so that the project remains easy to demonstrate.

Do not commit API keys or secrets.

---

# 2. read_file

Tool name:

`read_file`

Purpose:

Allow the assistant to inspect a file before asking the server to summarize it.

Input:

```text
path: string
```

Requirements:

* Read only files within an explicitly configured/allowed workspace directory.
* Prevent path traversal such as `../../secret.txt`.
* Return useful errors for nonexistent files.
* Avoid reading arbitrary files outside the configured workspace.
* Keep the implementation simple.

---

# 3. search_context

Tool name:

`search_context`

Purpose:

Search the configured workspace for a keyword or phrase.

Input should include something similar to:

```text
query: string
```

Optional:

```text
path: string
```

Requirements:

* Search relevant text files.
* Return matching file paths and useful snippets/line numbers.
* Ignore common generated/dependency directories such as:

  * `.git`
  * `node_modules`
  * `.venv`
  * `__pycache__`
  * build/dist directories
* Avoid over-engineering semantic/vector search.
* A straightforward keyword/text search is sufficient.

---
